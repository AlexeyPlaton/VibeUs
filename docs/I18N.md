# Internationalization (i18n) Guide

VibeUs uses `react-i18next` with an **English-first shipping contract**.

## Shipping locales

- `en.json` — canonical locale, default for unknown browsers, and runtime fallback.
- `ru.json` — fully supported Russian locale with exact key parity with English.

`zh.json` and `hi.json` are retained as translation work-in-progress, but V7 deliberately does **not** register or expose them in the runtime language switcher until each reaches 100% key parity and human language QA.

The active language set is defined by `SUPPORTED_UI_LOCALES` in `openspec-web/src/i18n/config.ts`. Do not create a second independent language list in product UI.

## Product copy rules

1. Add a semantic English key to `en.json`, for example `v7.dashboard.errors.projects_load`.
2. Add the exact same key to `ru.json` with the Russian value.
3. Render copy through `t`, `t18n`, `tr`, or `i18n.t`.
4. Never create new Cyrillic translation identifiers. Historical Cyrillic keys are retained only for persisted legacy compatibility and must not be referenced by new source code.
5. Do not hardcode user-facing Russian or English copy into React components just because the current screen has only one language.
6. Machine/protocol identifiers, brand names, code examples, provider names, and narrowly documented legacy matching regexes are not translation copy.

## Language is not billing market

UI locale and commercial market are independent dimensions. An English-speaking user may be eligible only for a RUB/Russia billing path, while a Russian-speaking user may later use a global merchant/payment path. `pricing.ts` therefore returns pricing data rather than localized UI sentences; pages format period/error labels through i18n.

## Legal documents

The Legal Center navigation is localized, but the currently binding hosted-service legal package remains the Russian-law/Russian-operator document set. English navigation or explanatory text is **not** a substitute for reviewed international Terms of Service, Privacy Notice, DPA, transfer mechanism, merchant/payment terms, or a non-RF data-region contract.

When a real international hosted commercial contour is enabled, create and legally review that document set against the actual operator, merchant, subprocessors, data region, cross-border transfers, taxes, refund policy, and payment provider. The self-hosted distribution remains governed by the repository license and self-hosting documentation.

## Adding a future shipping language

1. Copy the canonical `en.json` key structure.
2. Reach exact key parity.
3. Perform human language QA on landing, onboarding, dashboard, widget, error states, billing presentation, and Legal Center navigation.
4. Add the locale to `SUPPORTED_UI_LOCALES` and the widget switcher in the same change.
5. Extend V7 tests so a partial locale cannot be exposed accidentally.
