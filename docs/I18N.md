# Internationalization

VibeUs ships an English-first interface with Russian as a fully supported second locale.

## Shipping locales

- `en` — default for unknown browsers and runtime fallback;
- `ru` — supported Russian UI with matching product-copy coverage.

Chinese and Hindi locale files may exist as work in progress, but they are not exposed in the language switcher until they are complete and have been reviewed by a human speaker.

The active language set is defined by `SUPPORTED_UI_LOCALES` in `openspec-web/src/i18n/config.ts`. Product UI should not maintain a second independent language list.

## Adding product copy

1. Use a semantic translation key rather than putting user-facing copy directly into a React component.
2. Add the English and Russian values in the same change.
3. Render the value through the i18n helpers already used by that surface.
4. Keep translation keys language-neutral; do not create new Cyrillic identifiers.
5. Keep machine/protocol identifiers, code examples and provider names out of translation content unless they are actually user-facing labels.

Some larger UI areas use small TypeScript translation layers in addition to the base JSON dictionaries. The release tests validate the effective English/Russian key set, not only the two JSON files.

## Language is not billing market

UI language and commercial eligibility are independent. Choosing English or Russian never enables a payment provider, country, currency or tax mode by itself.

## Legal documents

A translated navigation shell does not create a new legal contract. Hosted international commerce should only be enabled when the actual operator, payment provider, data location, subprocessors, taxes and refund terms have been reviewed for that deployment.

## Adding another shipping language

1. Reach full effective key parity with the English UI.
2. Review the important journeys with a human speaker: landing, onboarding, dashboard, widget, errors, billing presentation and Legal Center.
3. Add the locale to `SUPPORTED_UI_LOCALES` and the widget language selector in the same change.
4. Extend the internationalization regression checks so a partial language cannot be exposed accidentally.

## Verification

The normal frontend suite includes the internationalization checks:

```bash
cd openspec-web
npm test
```

The full repository release checks also include them:

```bash
python run_release_gate.py
```
